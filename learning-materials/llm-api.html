Concept Learning Card

大模型 API 与提示工程（LLM API / Prompt Engineering）

通过接口（API）把请求发给大模型、拿回它生成的文本；而"提示工程"就是研究怎么写这段请求，才能稳定拿到你要的结果——零样本分类是它最常用的入门用法。

生成日期：2026-09-17 · 学习视角：大二学生第一次系统接触 AI · 资料来源均为公开可核查链接

01学习目标

  • 能说清"调用一次大模型 API"到底发生了什么：请求里放了什么、返回了什么、为什么按 token 计费。
  • 能写出一条合格的"分类任务提示"：角色 + 任务 + 标签定义 + 输出格式约束（必要时加示例）。
  • 能区分零样本（zero-shot）/ 少样本（few-shot）/ 微调（fine-tuning）三种做法，并说清什么情况该退回到更简单的那一种。

02核心问题

  • API 和"网页版对话框"有什么本质不同？为什么做批量任务必须用 API？
  • 提示工程到底在改什么？为什么同一件事换个写法，结果会差那么多？
  • 零样本分类"没训练过也能分类"，它靠的到底是什么？能信到什么程度？
  • 提示写到什么程度就该停下了——而不是一路往上堆复杂度？

03个人解释

我的理解：

我一开始以为"API"是个很高深的东西，用了才发现它的本质特别朴素：就是把你在网页对话框里打的字，用代码的方式发过去，再把回答接回来。区别只在于——网页版是给人用的，API 是给程序用的：它能批量跑、能被别的代码调用、能精确控制参数，也正因为如此，它的每一个字都要算钱。

大模型 API 我觉得最像点外卖：你写好一份订单（提示），骑手把菜送回来（模型输出）。订单写得越清楚——要什么菜、不要香菜、几分辣——拿到的就越接近你想要；写得含糊，就只能"看运气"。而"提示工程"就是研究怎么写这份订单的手艺。最关键的是我发现它不是玄学，而是可以被检验的：官方文档给的几条原则（说清楚、给理由、给例子、把结构和数据分开）都讲得明明白白 [来源 1][来源 3]。

而零样本分类让我最意外：我原本以为"模型没学过这个标签就分不了"，实际上它是把分类变成了一道阅读理解题——"这段文本是不是在讲『退款』？"——模型靠预训练时积累的语言能力和常识来判断 [来源 5][来源 6]。这也解释了它的局限：它判断的是"这句话像不像在讲退款"，而不是"这句话是否严格符合我们公司对退款的内部定义"。概念清楚，它就很准；概念模糊，它就靠猜。

作为大二学生，这是我第一次真正"用代码调用 AI"，而不是只对着网页聊天框说话。最大的收获反而跟技术无关：我意识到跟模型沟通和跟人沟通是同一件事——你以为说清楚了，其实对方理解的完全是另一套。以前我抱怨"AI 答得不对"，现在我会先回头看看是不是自己那句话有歧义。另一个提醒是"别过度工程"：Anthropic 那篇《Building Effective Agents》说先用最简单可行的方案，只在必要时才加复杂度 [来源 9]。这句话我现在会用来约束自己——能靠改一句话解决的，就别急着上微调。——杨国美

04核心机制 / 组成

① 一次 API 调用，其实只有两件事：你发过去什么、它传回来什么。

  • 你发过去：一条或多条消息（message），以及一堆参数（parameter）。消息分角色：系统消息（system / instructions）是"总规矩"，比如"你是一个严格的文本审核员"；用户消息（user）是具体要处理的内容。
  • 它传回来：生成的文本，外加一份用量信息（usage）——消耗了多少输入 token、多少输出 token。这就是计费依据。
  • 白话解释两个词：Token 是模型读写文本的最小单位，大约等于英文 4 个字符或 0.75 个单词，中文通常一个字到一个词；计费就是按 token 数算。官方文档里明确写了 token 同时影响"花多少钱""跑多久""能不能跑得通（不能超过上限）"[来源 8]。

② 提示工程的几条硬原则（来自两家官方文档的共识）。把两边对照着看，会发现重复出现的就那么几条 [来源 1][来源 3]：

原则白话解释反面例子 → 正面例子
说明确，别含蓄 把它当成"聪明但没有你背景信息的新同事"，你要什么就直接讲 「帮我总结一下」→「把这篇文章总结成 3 条要点，每条不超过 20 字」
给理由和上下文 说清"为什么这么做"，模型会自己推广到你的场景 「不要问密码」→「不要索取任何个人信息；需要时让用户去看帮助页」
用例子（few-shot） 给 3–5 个"输入 → 期望输出"的例子，格式和判断标准一次讲明 只说"按情感分类"→ 给 3 条带标签的样例
把结构和内容分开 用 XML 标签或 Markdown 标题把"指令 / 数据 / 例子"隔开，避免混淆 指令和待处理文本糊在一起 → 用 <data>…</data> 包住数据
规定输出格式 哪怕只说"只输出一个词"，也比让它自由发挥好——程序才解析得动 「分析一下这条评论」→「只输出：正面 / 负面 / 无关 三者之一」

OpenAI 的帮助文档把上手顺序总结得更直白：先用零样本试，不行再加少样本，还不行才考虑微调 [来源 4]。这个"由简到繁"的顺序很值得记住——它和《Building Effective Agents》里"先用最简单方案"是同一种工程直觉。

③ 零样本 / 少样本 / 微调：三种做法的取舍。

做法怎么做要不要标注数据什么时候用
零样本 zero-shot只写清标签和判断规则，不给例子不用快速验证可行性、标签含义本身就很清楚
少样本 few-shot在提示里塞 3–5 个示例只要几个，不用几千格式要求特殊、或"边界情况"需要示范
微调 fine-tuning用大量标注数据继续训练模型本身要很多（成千上万条）任务高频、量大、要求高且稳定，提示已经榨干

GPT-3 那篇论文第一次系统展示了这件事：模型规模足够大之后，不用更新任何参数、只靠提示里给几个例子，就能在大量任务上表现得很像样 [来源 5]。这就是"零样本 / 少样本"能成立的理论来源——能力本来就藏在预训练里，提示只是把它"引导出来"。

④ 零样本分类到底怎么工作的？以开源方案为例，做法是把待分类文本当成"前提"，把候选标签改写成一句话当成"假设"，然后让模型判断这个假设是否成立 [来源 6][来源 7]：

零样本分类的核心思路（不需要为标签训练）

待分类文本 + 候选标签 → 逐条组成「这段文本是关于 <标签> 的」→ 模型判断是否成立 → 得到各标签的概率

所以它"没训练也能分类"不是魔法，而是把分类问题翻译成了模型本来就擅长的判断/阅读理解问题。代价也很清楚：标签的措辞会影响结果（"退款"和"要求退钱"可能给出不同分数），而且它判断的是"字面语义像不像"，不是你公司内部定义的业务规则。

⑤ 为什么结果不稳定？大模型的输出默认是非确定性（non-deterministic）的——同样的输入，重跑一次可能不一样 [来源 8]。原因是采样时带有随机性。官方提供了 seed 参数想让结果可复现，但文档写得很实在：这是「尽力而为」，不保证完全一致，还要盯着 system_fingerprint 看后端有没有变过。所以：要做"必须一模一样"的事，就别把它交给模型自由发挥。

05应用场景（具体例子）

场景：还是「跳蚤市场」那个校园二手平台。这次运营同学不满足于"正面/负面"，想给每天 3000 条评价自动打上「物流 / 成色 / 描述一致 / 态度」四个主题标签，用来统计"哪类问题被吐槽最多"。

第 1 步 · 先写零样本提示（今天就能跑）。把四个标签的定义写清楚，并且强制输出格式：

你是二手交易平台的评价分析员。
请判断下面这条评价吐槽的是哪一类问题。
标签定义：
- 物流：快递慢、发错货、运输损坏
- 成色：实物比描述旧、有磕碰、有污渍
- 描述一致：描述与实物在型号/配件/容量上不符
- 态度：卖家回复慢、语气差、拒绝沟通
只输出一个标签名，不要任何解释。
<评价>{这里放这条评价}</评价>

为什么这么写：角色一句话（给它一个立场）、标签定义（消灭歧义）、<评价> 标签（把指令和数据分开）、"只输出一个标签名"（让程序能直接解析）——正好对应上面四条原则 [来源 1][来源 3]。

第 2 步 · 跑 200 条试水，暴露三个真实问题。

  • 格式跑偏：模型有时输出「这是一条负面评论，属于物流问题」而不是光秃秃的「物流」。程序直接解析失败。→ 修法：在提示里明确"不要解释"，并在代码里加兜底解析（从输出里搜有没有出现四个标签名），别假设模型每次都听话。
  • 标签撞车："收到时屏幕有裂痕，卖家说是运输问题"——既是物流也是成色。零样本下模型每次可能选不同的那个。→ 修法：在定义里补一条优先级规则（"同时符合多个时，优先判『物流』"）；或者改成允许多标签输出。这是提示层面能解决的，不用动模型。
  • 定义含糊的标签最不稳："描述一致"和"成色"在中文口语里经常混着说。→ 修法：加 少样本——塞 3 条容易混的例子并标好答案，模型立刻稳定很多（这就是"先零样本、不行加少样本"的实践 [来源 4]）。

第 3 步 · 算一下成本，再决定要不要全量跑 API。每条评价输入约 200 token（含标签定义），输出约 5 token。

  • 3000 条/天 × 205 token ≈ 61.5 万 token/天，一个月约 1850 万 token。
  • 把标签定义这种"每条都一样"的部分缓存起来、能省则省；真正要付费的差异部分其实只有评价本身。
  • 结论：如果日量再涨十倍，全量走大模型 API 会变得很贵。这时候的正确动作是先用 API 打一批标签当训练数据，再微调一个小模型长期用——也就是"由简到繁"的反向升级路径 [来源 4]。

第 4 步 · 必须留人工兜底。因为输出是非确定性的 [来源 8]，同一条评价今天判"物流"、明天可能判"成色"。所以：模型标签入库时保留置信度或原始输出，每周抽检 100 条人工核对；涉及"处罚卖家"这种后果重的动作，一定人工确认后才执行。

这个例子的完整取舍链：零样本（当天验证）→ 补标签定义和输出格式 → 加少样本稳边界 → 缓存省成本 → 量大后微调 → 全程保留人工兜底。每一步都是因为上一步"真的不够用了"才加的，没有一步是为了炫技。

06易混淆 / 使用边界

① API ≠ 模型。API 只是"通道"和"格式约定"；通道后面的模型会被服务方升级、替换。所以别把提示词的效果当成某个模型的永久属性——升级后可能要重新测。

② 提示工程 ≠ 上下文工程。提示工程管的是"这一条指令怎么写好"；上下文工程管的是"每一步该往窗口里放哪些信息"，是它的超集（详见本仓库《大模型的上下文》卡片）。做长任务或 Agent 时，后者才是主战场。

③ 零样本 ≠ 不用训练，也 ≠ 标签随便起。能力来自预训练，提示只是引导 [来源 5]；而标签的措辞直接决定结果好坏。同义词标签（"退款" vs "退货"）会给出不同判断，这不是 bug，是你没把概念定义清楚。

④ 温度设为 0 也不保证完全一致。官方文档把"可复现"写成"尽力而为" [来源 8]。需要严格一致的结果，应该用代码规则或结构化输出 + 校验来保证，而不是指望模型每次都一样。

⑤ 不要把该由代码做的事交给提示。"把日期格式化成 YYYY-MM-DD"、"算总和"这类确定性计算，用代码做又快又准。让模型做这类事，既贵又可能错。模型负责理解和生成，代码负责精确和一致。

⑥ 提示工程不是万能的，该承认的时候要承认。如果任务高频、量大、要求又高，官方给的建议顺序依然是"零样本 → 少样本 → 微调" [来源 4]；一直往提示里加字，最后会得到一段谁也不敢改的"咒语"，反而更难维护。

⑦ 成本与隐私是硬约束。token 就是钱，输入和输出都算 [来源 8]；同时你发给 API 的每一段文本都离开了本地——涉及个人隐私或未公开材料的内容，发之前要先想清楚。
